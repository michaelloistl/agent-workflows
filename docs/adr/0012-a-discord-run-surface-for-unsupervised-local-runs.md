# A Discord run surface for unsupervised local runs

ADR-0011 made a bare `implement-spec <n>` run the whole spec unattended, and recorded the consequence plainly: the assumption that a human sees a halt is now false by default. It left two things to make a halted run readable afterwards — the run log and the Herdr notification — and deferred the third to here: *"Richer reporting (a Discord hook) attaches at `record()` in `spec-loop-run.mts`, the single choke point every transition already passes through; nothing is built for it here."* This builds it, for local spec runs only, as a second surface shaped like the first.

## Status

accepted (extends ADR-0011 and ADR-0006; governed by ADR-0005's coupling rule)

## Context

A two-hour spec run that nobody is watching currently reports to three places, and each has a hole. The terminal has everything and is on a machine the developer has walked away from. The run log has every transition and is a file on that same disk, written and never read. The spec issue's progress comment is durable and remote, but it is a *rollup* — it says which slices are closed, not that the run stopped forty minutes ago and why. Herdr's notification is the only thing that pushes, and it only fires inside a Herdr pane, on the same machine, to a desktop the developer has left.

So the gap is specific: a run that halts while the developer is elsewhere tells them nothing until they come back and look. That is not a gap in the *record* — the record is good — it is a gap in *reach*.

The unattended CI path does not have this problem. A failed run sets `agent:blocked` and posts a comment carrying `See the run: $RUN_URL`, and GitHub emails on it. Reach is already solved there by the tracker.

This ADR also has to name a distinction the glossary was blurring. `CONTEXT.md` defines the **local sequencer** as attended and the **workflow sequencer** as unattended — an *entry point* distinction — and ADR-0011 then made the local entry point run without stopping, describing it as "unattended" in a different sense. Both usages are defensible and they are not the same axis. Attended still names the human's *ability* to intervene: same machine, same terminal, Ctrl-C, `--stop`. What ADR-0011 actually changed is whether anyone is *there*. That second axis needs its own word, because this surface exists only for one value of it.

## Decision

**The scope is local spec-loop runs. Not CI, not attended verb runs.** The surface reports what the `implement-spec` slice loop does on the developer's own machine. Extending it to the workflow sequencer was considered at length and rejected below; the short reason is that CI's reach problem is already solved and the cost of solving it again is paid in every consuming repo. Attended single-verb runs (`implement 139`) are minutes long and typed by hand, so the developer is plausibly still at the terminal; they are excluded for now, and adding them later is a call site, not a redesign.

**One-way, over a Discord incoming webhook, with no bot.** The surface posts and never listens. `--stop` from a second terminal is already the way to stop a run, and a bot would mean a token, a gateway connection held open for the length of the run, and a listener inside a loop whose defining rule is that nothing may delay it.

**A forum channel, one thread per run, with the thread id held in memory.** This is forced, not preferred: an incoming webhook can only create a thread where the channel is a forum or media channel (`thread_name` is documented as requiring it), and there is no endpoint of any kind that finds a thread by name — enumeration lives under `/guilds` and `/channels`, which a webhook token cannot reach. A thread id is therefore knowable only at creation and only via `?wait=true`, whose returned message `id` *is* the thread id. Because a single local process owns the run from kickoff to final PR, that id can simply live in a variable. Nothing is persisted, and the *no local state* rule (ADR-0006) is untouched — it governs resume state, and this is not state anything resumes from.

**The thread is created at kickoff, before the preview prints, with one retry.** Ordering is the whole point. A forum channel accepts no message outside a thread, so a failed create silences the entire run — including the halt notification the surface exists to deliver. That failure is therefore made loud at the one moment the developer is still looking: the preview, which ADR-0011 already prints on every run and already names the run log's path for exactly this reason, gains a line stating `discord: spec #94 thread created` or `discord: off (…)`. A create that fails twice disables the surface for the run and says so; it never halts the run.

**Five events.** `run started`, `slice building`, `slice merged`, `halt`, `complete`. The three progress events post as plain content; the two terminal ones as embeds, because colour is what makes an unread channel scannable — **red for a halt, amber where the halt's reason is a refusal, green for a completion**. A refusal is not a failure (`CONTEXT.md`), and under the spec loop it arrives as a *halt reason* rather than a distinct outcome, so the distinction is carried by colour instead of by a sixth event.

**A halt sends its reason's first line, truncated, plus the run-log path and the issue link — never the full text.** Halt reasons are assembled from agent and CI output, so their contents are not bounded by anything in this repository, and Discord is a third party that may retain what is posted after it is deleted. The message's job is to make the developer look; the run log and the issue comment remain the record and are unchanged.

**Two loud exceptions to silence, and no others.** The surface inherits Herdr's three rules verbatim — silent no-op when unconfigured, never fail or delay a run, no new dependency — with the failed thread create above as the first exception, and an HTTP `404` as the second: it disables the surface for the process and prints one line to stderr. Discord documents that a webhook returning 404 must not be retried, on pain of an IP-level restriction, and a deleted or rotated webhook otherwise fails silently forever, which is the worst diagnostic case this design has.

**Every send carries `?wait=true`, with a 2s timeout and no retry.** The default, `wait=false`, "does not return an error" for a message that was not saved — silent loss, in a surface whose entire value is that it is trusted. Awaiting is also deliberate: an un-awaited request in a process that exits through `finish()` can be killed before it leaves, which would drop precisely the halt notification. The budget is generous rather than tight — a measured send round-trips in about 0.4s — because the timeout exists to bound a network that has stopped answering, not to bound a normal send.

**The credential lives in `.sandcastle/.env`, and the sequencer learns to read it.** `DISCORD_WEBHOOK_URL` sits beside `CLAUDE_CODE_OAUTH_TOKEN`, gitignored by `.sandcastle/.gitignore`, documented as a commented line in the committed `.env.example`. This required a change: sandcastle's `resolveEnv` merges that file into the *agent's* environment inside `run()` and never touches the calling process, so the sequencer — which is what emits all five events — could not see it. The sequencer now loads the file at startup, applying file values **over** `process.env` to match sandcastle's own precedence, so one key never resolves two ways depending on which process reads it. It is not a `config.json` key: that file is committed, and this is a credential.

**A standalone module, not an abstraction shared with Herdr.** `src/sequencer/discord.mts` mirrors `herdr.mts` in shape — pure message builders, an injected transport, a factory that returns an inert surface when unconfigured — without either depending on the other. Herdr's central act is renaming a pane, which does not generalise, and a shared interface whose methods half its implementations ignore is worse than two small concrete files.

## Considered alternatives

- **Cover CI runs too.** Genuinely attractive, and taken as the decision for part of this design session before being reversed. Rejected because almost none of the cost is Discord: the URL becomes a GitHub secret that every consuming repo must hold, declared and passed by name through every thin caller — `secrets: inherit` does not cross an owner boundary — generated by `callers.mts` and rolled out by `sync`. It also forces the thread id to become distributed state, since CI processes are ephemeral and per-slice, which means a marker convention in the spec issue and a tracker read on the notification path. All of that to duplicate reach the tracker already provides through `agent:blocked` and `$RUN_URL`. The marginal value of this surface is highest exactly where nothing currently reports at all.
- **A flat text channel, no threads.** Zero new failure modes, works in an ordinary channel, and every message independent — a failed send loses one message rather than a run. Rejected on volume: a 26-slice spec emits roughly 54 messages, interleaved with any concurrent worktree, which is a channel that gets muted within a week. That said, this is the closest call in the ADR, and the forum choice buys grouping at the price of an all-or-nothing dependency on one create. The loud preview line is what makes that price acceptable rather than hidden.
- **Persist the thread id in the tracker.** Consistent with how `resume` already works, and necessary the moment CI is in scope. Rejected as unnecessary here — one process owns the whole run — and as actively risky under a 2s swallow-everything timeout, which cannot distinguish "the create failed" from "the create succeeded slowly", so a retry writes the wrong id or leaves a duplicate forum post.
- **One message per run, edited in place into a live rollup.** Tempting because `spec-report.mts` already renders exactly that rollup for the spec issue. Rejected: editing requires retaining the message id, a single failed edit silently loses every subsequent state change, and the docs warn that an edit re-parses mentions unless `allowed_mentions` is re-sent each time. A rollup that is sometimes stale is worse than a log that is always complete.
- **A bot instead of a webhook.** Buys thread creation in ordinary text channels, thread lookup, and two-way control. Rejected as a much larger dependency for a surface that must be droppable, and directly against ADR-0005's rule below.
- **Per-repo webhooks rather than one.** Would shrink the blast radius of a leak. Rejected under local-only scope, where there is one machine and one file; it multiplies rotation — which is manual — for no containment that matters.

## Consequences

- **ADR-0005's coupling rule is what makes this admissible, and it is the test any future surface must pass.** That ADR permits *contact* with an external UI and forbids *dependency* on one: "Emitting progress into a multiplexer's UI when one happens to be present is permitted and cheap; needing one in order to work is not." Discord is contact. The run must behave identically with the variable unset, and the two loud exceptions above report the surface's own health without ever changing the run's outcome.
- **A leaked webhook URL is bounded to one channel, and cannot be rotated in place.** Anyone holding it can post, impersonate via the per-message `username` and `avatar_url` overrides, read back, edit and delete the webhook's messages, and permanently destroy the webhook. They cannot move it: `Modify Webhook with Token` refuses a `channel_id`. There is no reset-token endpoint anywhere in the webhook API, so rotation is delete-and-create, which yields a wholly new URL that every holder must be updated to. Under local-only scope that is one line in one gitignored file.
- **The sequencer now reads `.sandcastle/.env`.** A new capability, with precedent — `shared/config.mts` already reads `.sandcastle/agent-workflows/config.json` — and a new failure mode worth naming: a key set in the shell but absent from the file resolves differently than a reader might expect, because the file wins. That is sandcastle's rule, deliberately matched rather than improved on.
- **A resumed run opens a second thread.** The thread id is the one thing that does not survive a halt, since resume derives from the tracker and the branches alone. A resumed spec posts to `spec #94 (resumed)`. Accepted as the price of persisting nothing.
- **Discord's duplicate-thread behaviour is undocumented, and was verified by probe rather than assumed.** The API says a thread with the given name "will be created" and says nothing about reuse. Executed twice against a live forum channel with the same `thread_name`, the second call returned a *different* thread id — so `thread_name` is not an idempotency key, and a retried create that had actually succeeded leaves a duplicate post. That is why the retry is once, and only on the initial create. The same probe confirmed the other undocumented equality this design leans on: the returned message's `channel_id` equals its `id`, both being the new thread's id.
- **The channel must be a forum channel with `REQUIRE_TAG` off.** A manual setup step on the developer's Discord server, and a real constraint: pointing the variable at an ordinary text channel produces a surface that creates nothing and reports `off` in every preview.
- **`CONTEXT.md` gains two Observability terms.** *Run surface* names the category — a best-effort outbound report of a run's progress, of which Herdr and Discord are the two instances — and is deliberately distinguished from the *run log*, which is written and never read, and the *progress comment*, which is tracker state. *Supervised / unsupervised* names the axis this ADR's Context describes, orthogonal to attended/unattended, which keeps its entry-point meaning unchanged.
- **Attended verb runs remain unsurfaced**, and the asymmetry is deliberate rather than an oversight. If it starts to bite, the fix is a call site in `attended.mts`, not a change to anything decided here.
