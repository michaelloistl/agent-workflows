# A read-only terminal status view, piloting native issue hierarchy

The fleet's only cross-cutting progress surface is the **progress comment** the orchestrator posts on each spec issue — readable, but only one spec at a time and only in a browser. This adds a third entry point to the package: `agent-workflows status`, a one-shot terminal view of the specs currently building and the state of each of their tracer-bullets. It is read-only, it reads GitHub and nothing else, and it deliberately reads the **native** parent/sub-issue hierarchy first — making it the zero-risk pilot for a migration the orchestrator will make later.

## Status

accepted

## Context

Running the fleet AFK means the interesting question is never "what is this run doing" — the Actions UI answers that — but "which of my specs is mid-flight, how far in, and is any of them stuck". Today that is assembled by hand from a spec issue's progress comment, the issue list's `agent:*` labels, and a PR list.

Three properties of the existing code make a terminal view cheap. `spec-graph.mts` is already the pure brain (`tracerBullets`, `nextSlice`, `topologicalOrder`) with no `gh` in it. `resolveRepoSlug()` already infers the repo from the git remote. And `spec-report.mts` already renders essentially the view we want, just into markdown for a comment.

One property of the tracker made it much cheaper still, and was discovered while designing this. GitHub's native sub-issue hierarchy is exposed through `gh` 2.94+ (`--json parent,blockedBy,blocking,issueType`) and the REST `sub_issues` endpoint — and in `madebyon/on-vantage` it is **already populated**, mirrored by the Linear sync. `gh api repos/madebyon/on-vantage/issues/1438/sub_issues` returns all five tracer-bullets with their states, including the closed one. Native `blockedBy`, by contrast, was empty everywhere at the time of this survey: the feature existed, nothing wrote it. *(That expired — see the #99 amendment under Decision.)*

That single fact removed the hardest problem in the design. Rendering a spec's finished slices needs issues that are no longer open, and scanning a 1,500-issue repo for them is not viable; the fallback under consideration was reading the last progress comment as a cache, with all the staleness that implies. The native endpoint returns them directly.

## Decision

**Scoped to specs, and to the repo you are standing in.** The view lists specs currently being built with their tracer-bullets nested beneath, and nothing else — no standalone issues, no un-parented agent PRs. Multi-repo aggregation and a flat remainder section are both plausible later additions and neither is built now; the structure keeps them additive.

**A running spec carries no label, so discovery is by branch.** `kickoff.mts:51` removes `agent:implement-spec` the moment it fires, so filtering specs by `agent:*` matches exactly zero specs, always. The first design walked up from labelled slices to their parents instead; slicing the work revealed that this cannot reach a spec whose tracer-bullets have *all* closed — which is precisely the `awaiting final PR` state below, so the state and its discovery rule contradicted each other. Discovery is therefore **an open spec issue with a live `agent/spec-*` remote branch**: a branch exists only after kickoff, so that set is exactly the in-flight specs, and `remoteBranches()`/`specNumberFromBranch()`/`pickSpecBranch()` already exist. Labels are still read — for per-slice *state*, not for finding the spec. This needs no new label and no new convention.

**No triage labels are read.** `ready-for-agent` here and `ready-for-afk` in `on-vantage` is real drift that `docs/agents/triage-labels.md` exists to absorb. Deriving membership structurally means the view never sees a triage label, so the drift cannot reach it and no config field is needed to paper over it.

**Membership is native-first with a textual fallback; ordering unions the two sources.** A slice's parent resolves as `native parent ?? parentRef(body)`. (Sequencing note: the walking skeleton shipped the textual arm alone and #96 added the native one — the fallback is what made that order safe, since the view is never empty in a repo the native read cannot see.) This makes migration gradual and per-repo rather than a flag day, and means the view is never silently empty in a repo that has not caught up.

*Amended by #99.* This ADR originally kept ordering textual, on the finding that native `blockedBy` was empty everywhere — the feature existed, nothing wrote it. That premise expired: issue dependencies went GA in August 2025, `gh` exposes `blockedBy` on both `issue view` and `issue list`, and this repo's own spec #94 carries native dependency edges on its tracer-bullets. A slice's blockers are therefore the **union** of its native `blockedBy` edges and the refs in `## Blocked by` — deliberately *not* the `native ?? textual` rule membership uses, and named `unionBlockers` so it cannot be read as one. Parent is a single value, so a fallback is safe there; blockers are a set whose failure modes are asymmetric — over-blocking is a deadlocked row a human reads and clears, under-blocking silently builds a slice on a dependency that has not landed. The union is the conservative side of that. A native blocker in **another repository** is excluded rather than ordered on, since issue numbers are per-repo and gating this spec's `#12` on someone else's would reorder the build around a coincidence — and it travels with the edges as `owner/name#12` so that every surface names it: the status view's row and the spec's progress comment both show what the order declined to wait for. Dropping it in silence would leave the orchestrator dispatching a slice a human believes is gated.

What does not change is where the order is computed: the view sorts with the same `topologicalOrder()` the orchestrator uses, and both now read the same edges. The alternative — displaying the native sub-issue *priority* order — is rejected outright: a view whose "next" row disagrees with `nextSlice()` is worse than no view, because it is confidently wrong about the only thing anyone reads it for.

**A spec is identified by having sub-issues**, `subIssuesSummary.total > 0`, unioned with the existing structural scan. `guards.mts:53` already issues this query. This preserves `CONTEXT.md`'s rule that a spec is recognised structurally rather than by a title prefix or a label — native hierarchy is structure, better typed.

**The view is a pilot, so it shares a reader rather than owning one.** The union logic lands in a new `shared/spec-tree.mts` — given a repo, the specs and their slices with states — which the status view consumes now and the orchestrator migrates onto when native parents are written rather than merely read. A pilot running on its own private reader would prove nothing about the code that eventually matters.

**Data is shared; rendering is not.** `spec-report.mts` keeps emitting markdown checkboxes for the progress comment; the status view gets its own terminal renderer with alignment, colour and `agent:*` states. One function serving both a comment body and an ANSI terminal makes both worse. This is the decide/dispatch split ADR-0006 credited in `advance.mts`, applied to output.

**Read-only, one-shot, `--watch` to redraw.** No key applies a label, because a label write *is* a dispatch — one stray keypress would start a real, billed agent run — and because writing labels would put tracker semantics in a fourth place. Nor is there any key handling: a one-shot command has no input loop, so each row simply carries its issue URL for the terminal to make clickable. *Amended by #105.* That URL first shipped as a visible trailing column, ~50 characters wide; #105 moved it into an OSC 8 hyperlink attached to the issue reference itself, so `#1521` is both what you read and what you click, with the state marker left outside the link. The column survives only as the fallback click target: hyperlinks are emitted just as colour is, when stdout is a terminal, and when they are off — a pipe, a redirect, or `--no-hyperlinks` for a terminal that ignores the escape — the column is printed exactly as before, so a reference is never left unreachable. The no-key-handling reasoning is unchanged: the row still hands the terminal a URL rather than interpreting a click, only through the escape instead of a column. *Amended again — the terminal is not always what reads the escape.* #105 assumed a terminal either honours OSC 8 or ignores it harmlessly, so a TTY check decides. A **multiplexer** breaks that. Measured against Herdr 0.8.0 under Ghostty, an OSC 8 link inside a pane opens on **neither** route: not on ⌘-click, which Herdr receives and does not act on, nor on ⌘-Shift-click, which bypasses Herdr's mouse capture and reaches the host terminal with no hyperlink to find. Herdr's own plain-URL clicking works on both routes, so inside Herdr the URL column is a *working* click target while the escape is an inert one — meaning the TTY default landed on precisely the combination #105 existed to prevent, a row carrying neither a link nor a URL, in the very surface the change was made for. Hyperlinks therefore default **off** when `HERDR_ENV=1`. That is capability detection, which this ADR rejected — but what it rejected was a table of terminal *names* that goes stale in silence. This is one variable the multiplexer sets about itself, it fails toward the URL column rather than toward an unreachable row, and `--hyperlinks` forces them back on the day Herdr fixes this, so the rule going stale costs a flag rather than a release. One-shot output first, before committing to a render loop, resize handling and input: the content has to be proven right before the surface is worth building. Fetch cost, once #96 landed, is one `git ls-remote` plus at most three calls per visible spec — the issue itself, its `sub_issues`, and its timeline — with a full-repo issue scan only for a spec that has no native hierarchy at all, so a 30s `--watch` interval is affordable against the rate limit.

*Amended by #106.* That per-redraw cost was the cost of a `--watch` **tick**, on the premise that a tick and a fetch are one thing — every redraw does the full pass. #106 separates them: a tick now first asks one cheap question — has anything changed? — and does the full pass only when the answer is yes or cannot be trusted. The question is answered by two probes, neither of which is a fresh fetch. The remote branch list is a `git ls-remote` the pass already makes every tick, and it catches a spec starting or a branch disappearing. One conditional GitHub read — the repo's issues ordered by most-recently-updated, a single item, replayed with the previous ETag held in memory — catches everything else, because any label write, close, reopen, body edit or new issue makes that issue the head of an updated-descending list; a `304 Not Modified` costs nothing against the primary rate limit, so an idle watch consumes none of it and can run indefinitely. The sentinel is an invalidation signal and never a source of display data: the full pass remains the only thing that produces a frame, so what `--watch` shows stays exactly what a one-shot run prints. The cheap path fails open — a probe error, a missing ETag, an unparseable response, or the first tick all force a full pass, because over-refreshing costs a handful of calls while under-refreshing is invisible — and a staleness ceiling forces a full pass periodically regardless, so a change the probes cannot witness costs latency rather than a frozen screen. The probe over-triggers by design: the issues endpoint includes pull requests, so an unrelated PR comment causes one extra full pass. Interval defaults and the floor were untouched by #106, which changed what a tick costs, not how often one happens — but #107 then brought both down now that the tick is cheap: the default drops to 5s and the floor to 2s, its justification changing from the shared rate limit to the round trip of the tick itself (see the Consequences amendment).

**Shipped as a dispatcher subcommand.** `agent-workflows status`, inside the package's `files:`, exposed as `yarn agent:status`. Since the view reads the repo it is standing in, shipping it to consuming repos is what makes it work in `on-vantage` at all.

**Row states are labels and issue state only.** No PR or check-run join. A slice is `closed`, `open`, or its `agent:*` label, with `agent:blocked` rendered loudly because it is the one state meaning *stop and look*. Joining the building slice to its PR and checks would answer "why is it stuck" and is the most likely first extension; it is not in the first version.

*Amended — the final PR is now shown, the check-run join still is not.* The half of this decision that gave the view its blind spot was the spec row, not the slice rows. `awaiting final PR` means "every slice closed while the spec issue is open", which is true both before advance opens the final PR and forever after — so the row went on saying *awaiting* at a PR that had been sitting open for days, naming the wrong party as the one holding things up. The view now reads the final PR and gives it a row of its own beneath the slices, and `awaiting-final-pr` narrows to what it always claimed: all slices closed, no PR yet, which is a real and occasionally *stuck* state (advance failed to open it). The new `final-pr-open` covers the rest.

It is found by its **head and base branches** — an open PR from the spec branch to the base advance opened it against — which is the predicate `openFinalPr` already uses for its own idempotency check (`--head <spec branch> --base <base> --state open`), and deliberately not the `agent:review-pr` label. That label is a *trigger* label: the review run retires it as it starts, and `finalPrReview: false` suppresses it altogether, so it identifies the PR only during the window it is being consumed. The base has to be in the predicate rather than the head alone, because GitHub allows exactly one open PR per head/base pair — so a *second* PR off a spec branch is by construction one somebody opened against something else, and it is easily the OLDER of the two (a human opens theirs while the spec is still building; advance opens the real one when the last slice closes). Matching on the head alone and tie-breaking on the lowest number would then name the human's PR as the spec's final PR, with the wrong title and the wrong state, at exactly the moment the spec completed. The view resolves the base the way `openFinalPr` resolves it — the configured base branch, else the repository default — once per process and lazily, inside the gate below, so an unresolvable base degrades to a head-only match (the lowest number is the tie-break there, and the only place it survives) rather than leaving a spec reading `awaiting final PR` forever. The read is one `gh pr list`, not one per spec, and it is **gated**: a final PR cannot exist before the last slice closes, so a pass with no complete spec makes no PR call at all — which is every pass of a watch on a spec that is still building. A PR a human opens off the spec branch early is therefore invisible, accepted knowingly rather than paid for on every tick.

What this does **not** take is the check-run join, and the reasoning above is the reason: rows are still assembled from what one list read already carries. Draft-versus-ready and `reviewDecision` come free on the PR record and answer "is a human the gate or am I", which is the question the row exists for; checks would cost a call per PR to answer a different one. Two known gaps stay open. A final PR **closed without merging** leaves the spec open with no open PR, so the row reverts to `awaiting final PR` — misleading, but it costs the whole repo's PR history to detect a state a human created deliberately and already knows about. And a review submitted on the PR may not bump the `updated_at` the `--watch` freshness probe reads, so an approval can lag by up to the staleness ceiling; a second conditional probe against `/pulls` would double the per-tick cost the #106 design exists to avoid, to shave five minutes off news that is not urgent.

*Amended — the view now reads one thing that is not GitHub.* This ADR opened by saying the view "reads GitHub and nothing else", and that rule is deliberately broken here: the view leads with the account's **quota headroom**, the share of its rolling session and weekly limits still unconsumed. The justification is that the tree cannot answer the question the headroom answers. Every verb runs the `claude` CLI on the runner under `CLAUDE_CODE_OAUTH_TOKEN` — a subscription token, not a metered API key — so the fleet drains the same windows the operator's interactive work does, and it drains them *without touching the tracker*: a CI run consuming a week's headroom changes no label, closes no issue, and moves no row. A view assembled purely from GitHub is therefore structurally blind to the one thing that can strand every spec on screen at once. "Five specs in flight" and "39% of the week gone" are only worth anything together.

The source is `claude --strict-mcp-config --print --output-format json "/usage"`, and three properties of it decide the shape. It makes **no model call** (`num_turns: 0`, `duration_api_ms: 0`) so reading headroom never consumes headroom. That claim is exactly as wide as the evidence: it is about the rate-limit windows the line reports, and it is *not* verified of the request and session tallies the same output carries (`Last 7d · N requests · M sessions`), which are a different counter. If a `--print` invocation registers in those, an overnight watch adds one per 30s window to them — annoying in a report, but not a claim on the windows the line is read for, and the 30s throttle is what bounds it either way. It needs **no persistence** — the point-in-time read is the whole state, which is what keeps `CONTEXT.md`'s rule that resume state is derived and never written to a local file intact; this ADR would have been much harder to justify otherwise. And it costs **~1.4s of wall clock**, nearly all process startup, which is the number that shapes the rest: MCP servers are disabled for the call because loading a consumer's Linear plugin to ask the local account about its own rate limits is pure startup cost (~3.4s with them, ~1.4s without, byte-identical output), and a `--watch` tick reuses a read for 30s rather than paying it every 5s. That throttle is deliberately *not* the #106 freshness gate: that gate exists to spend the shared GitHub rate limit and asks "has anything changed", while this is a wall-clock throttle on a local subprocess for which the read *is* the probe. It stays outside the gate because the number moves precisely when the tree does not — gating it behind the frame cache would freeze the one figure the watch was opened for.

Two consequences of it being account-global rather than repo-scoped. It renders as a **line above the tree, never a column**: it has no per-spec meaning, so there is no row it could belong to, and the tree's column budget (`TITLE_WIDTH = 56`) is untouched. And it is **suppressible with `--no-headroom`** — not merely to save the subprocess, but because the headroom read is of whichever account is authenticated *locally*, which in a consuming repo whose CI runs on a different subscription is a true number that says nothing about the fleet on screen. The flag is named for the concept rather than for `/usage`, because `CONTEXT.md` rules that word out for this and a flag name is the hardest thing here to change later.

The line itself, though, states each window in the **complement of the concept** — `week 39% used`, not `61% left` — and the word `used` is load-bearing rather than filler. The source reports consumption, the colour ramp runs upward with it, and a bare `week 39%` beneath a line labelled `quota` is read as "39% left" as readily as "39% gone". Inverting the figure instead was the other consistent option and was rejected: it would put a number on screen that no other surface — `/usage`, the statusline payload, the plan's own wording — agrees with, to save one word.

Every failure resolves to **omitting the line in silence**: `claude` absent from the PATH, unauthenticated, authenticated to something with no subscription windows (an API key, Bedrock, Vertex), timed out at 4s, or prose this release no longer recognises. That last one is the standing fragility and it is named rather than hidden — the command returns its windows as rendered English in a `result` string, not as structured data, so this parses text a future release may reword. A partial parse is refused as hard as a failed one: a session bar with no weekly bar reads as "the week is fine", which is the single wrong impression this must not leave. Under CI, or for a consumer who never authenticates the CLI, the view degrades to exactly what it printed before this existed.

Silence is the right answer for a *standing* failure and the wrong one for a blip, which is the one place the throttle does more than ration: it carries the last good line across exactly **one** failed window. Under `--watch` a single 4s timeout would otherwise drop the line and shift the whole tree up two rows, unexplained, on the surface where the number is being watched hardest. One window of carry absorbs that; a second consecutive failure drops the line, so a CLI that has genuinely stopped answering cannot leave a percentage on screen that the reader has no way to tell is an hour stale. The 4s timeout is also *not* bounded by the `--interval` floor of 2s: a bound that tight is no slack at all against a 1.4s measured read, so the accepted worst case is that one tick per 30s window hitches for 4s on a machine where `claude` is installed but wedged.

**A finished spec is kept visible.** A spec whose slices are all closed while its issue is open renders as `awaiting final PR` — the moment a spec needs a human must not be the moment it disappears. Branch-based discovery is what makes this reachable, and it also removes the gaps a label-driven rule would have had: under labels a spec would blink out during `advance` and during the CI-gate wait, which the first draft accepted as self-correcting. They now cost nothing to eliminate.

## Considered alternatives

- **`gh-dash`.** Sections are raw GitHub search filters, so multi-repo is free and keybindings can shell out to anything. Rejected as the primary surface for two structural reasons: a flat search query cannot express a parent→child rollup, and it cannot join an issue to its PR and checks into one row. Still worth a config as a cheap falsifier for the flat half of the problem, which this view deliberately does not cover.
- **Reading the last progress comment as the source of closed slices.** Nearly free and already rendered. Rejected once native `sub_issues` proved to return them directly: the comment is a cache that goes stale between advances and is absent on a spec that has never advanced — lying exactly when a run is in trouble.
- **Walking up from `agent:*`-labelled slices to their parents.** The original discovery rule, replaced during slicing: it cannot see a spec whose slices have all closed, so it contradicted `awaiting final PR`. The objection that sank branch-based discovery first time round — `spec-1198`'s branch outlives its issue, so the branch set contains ghosts — is answered by requiring the spec *issue* to be open, which excludes exactly those ghosts.
- **Migrating the orchestrator to native parents first, then building the view against clean data.** Rejected as the wrong order of risk. The view is read-only; a misread renders a wrong list and nothing else — no branch, no merge, no agent run. Piloting the native edge here first is close to free, and a correct tree drawn from native data is the evidence the orchestrator migration needs.
- **Reading quota headroom from the statusline payload.** Claude Code hands a JSON blob to a user's statusline command that carries `rate_limits.five_hour` and `.seven_day`. Rejected once the non-interactive `/usage` route was found to work: the statusline is **push, not pull**, so a standalone command cannot ask for it — the only architecture available was a statusline shim writing a cache file for the view to read. That would have meant the system's first persisted local state, a setup step in the user's *global* `~/.claude/settings.json` that a git-dependency package cannot perform for its consumers, and data only as fresh as the last interactive session — frozen under `--watch` while the fleet drained the very window on screen. It also drops the per-model window, which the interactive view shows and the statusline projection does not.
- **Deriving cost from token counts.** `sandcastle`'s `RunResult.iterations[].usage` already carries input, output and cache tokens at every `run()` call site, discarded today. Rejected as a different feature answering a different question: with subscription OAuth there is no billing surface to reconcile against, so a dollar figure would have to be modelled from a price table this repo does not have — and headroom, not spend, is what decides whether to let a spec finish.
- **A headroom ceiling in the sequencer.** `runCeiling` already halts an attended run at N slices or M seconds, and quota is the more meaningful bound than wall clock. Rejected because a CI runner has no authenticated interactive CLI to read headroom from, so the bound could never exist on the path that spends the most of it. Display only, and the reader is deliberately left in `src/status/` rather than `src/shared/` so no seam implies otherwise.
- **A persistent TUI.** Rejected for now: a much larger commitment to input handling and layout, taken before anyone knows whether the content is right.
- **Multi-repo aggregation.** The one thing a browser genuinely cannot do, and still rejected for v1 — the spec rollup is the sharper product and it is what makes the view worth building at all.

## Consequences

- `CONTEXT.md` gains **status view** and **spec tree**, and the spec issue's rollup is renamed the **progress comment** — the name the code has always used (`renderProgress`, `spec-report.mts`), while only the prose called it a dashboard. That collision is resolved before two things share one word.
- `CONTEXT.md`'s *Tracker-agnostic* entry is corrected. "Performs zero tracker reads or writes" is true of the reusable **workflow** and has been false of the **package** since the hooks moved into it — twenty files under `src/` shell out to `gh`. The status view is the third place this is true and the first that is not a hook, so the claim is restated rather than quietly broken again.
- The package acquires a non-verb, non-orchestrator entry point. `status` runs no agent and follows no hook contract; like `implement-spec` it is reached through the dispatcher without being a sixth verb.
- Two sources of truth for the spec graph coexist during migration — native parent and `## Parent` — and the union reader is the only place that knows. When `/to-tickets` starts writing native parents, the textual arm becomes dead weight rather than a second contract.
- Mixing the two *within one spec* is the case that decides whether the native fetch can be trusted, and #96 found it is not enough to fetch sub-issues alone: a slice added since the last sync is textual while its siblings are native, and a native-only fetch drops it — a wrong count and a wrong "next" row, which is the failure this view exists to avoid. The spec's own **timeline** closes it: a `#N` in a body is a cross-reference event on issue N, so one call per spec finds every candidate child without a scan. It is a candidate list, not a child list — a follow-up that merely mentions the spec comes back too — so the `## Parent` parse still decides membership.
- `--watch` (#98) is a redraw and nothing more: it repeats the same pass, swaps to the alternate screen so the user's scrollback survives, and touches stdin never — which is what keeps "no key handling" a property of the code rather than a promise. Two rules follow from the surface it draws on: it is **refused when stdout is not a terminal**, because replacing a frame in a pipe is impossible and appending one every few seconds is worse; and the interval has a **2s floor** — no longer because of the shared rate limit, which a free `304` retired (#107), but because an interval shorter than the round trip of the tick itself would only stack checks on top of each other. A failed read is drawn in place rather than ending the watch — an overnight pane must survive a dropped connection. *(#106 kept every word of this true of the redraw loop itself, which is unchanged, while making a tick decide whether to repeat the pass at all — see the amendment above. The loop's contract already accommodated a wrapper that decides whether to do real work: a render function it calls once per interval, allowed to throw. Its footer stays truthful because an unchanged frame has been positively verified as current rather than assumed.)*
- Native dependencies are now populated and read (#99), which retires the consequence this bullet used to record. The two halves of the hierarchy migration are still two jobs — membership went native-first in #96, dependencies union in #99 — but neither is speculative any longer, and the orchestrator picks the dependency change up with the view because both call one `tracerBullets` with the same edge rules. Writing native edges remains nobody's job: `/to-tickets` still declares blockers textually, so the union's textual arm carries every spec the fleet creates itself.
- A native edge can point anywhere in the repo, where a hand-written `## Blocked by` points at a sibling slice. `nextSlice` has always ignored blockers outside the spec's own slice set — the pure module must not deadlock on a stray ref — so a slice natively blocked by an issue that is *not* a tracer-bullet of this spec is ordered as though unblocked. That is the `implement` blocked-by guard's job, not the graph's, and it is the one exclusion the ordering makes silently: unlike a cross-repo blocker it is a local issue a human can find from the slice itself. #100 took the guard onto the union so it can do that job: it was the last reader of a dependency edge with a private copy of the body parse, and a slice blocked only natively walked past it. The two readers now share the rule and keep their different questions — the graph asks which of a spec's own slices go first, the guard asks whether *anything* still gates this one run — which is also why the guard is where a blocker outside the spec is caught. The gap closed is defence in depth, since ordering would not have dispatched such a slice anyway; it matters on the attended and manual paths, where a human names a slice and the guard is the only thing in front of the run. Reading the shared rule also retired a fan-out: the guard read one issue per blocking ref for its state, and states arrive with the edges — natively in the `blockedBy` node itself, textually in the issue list the guard already reads to detect a spec. That list is a *page*, though, so the point read survives as the exception for a ref past its end: unlike ordering, the guard treats an unresolvable ref as not blocking, and a blocker that merely scrolled off a page would take the same exit and under-block in silence. The state carried on a native edge is trusted over the page for the same reason.
- `CONTEXT.md` gains **quota headroom**, and the entry has to hold a line against **run ceiling**: a ceiling bounds one run, headroom bounds all work everywhere. Naming them apart matters because the obvious next thought — "make the ceiling a quota ceiling" — is the alternative rejected above.
- The view's read surface is no longer one source, and the *Status view* glossary entry's "Reads GitHub only" is corrected rather than quietly broken. What survives intact is the stronger rule: it still **writes nothing**, and the second source is a read that makes no model call, so watching remains free of dispatch in both the tracker sense and the billing one.
- The read surface widened once more with the footer's **running package version** (#121), and the *Status view* glossary entry is corrected again rather than left one source behind: the third read is the executing package's own manifest, off local disk, and it is what neither the tracker nor the network can answer — which copy of the code drew this. It changes nothing this ADR governs: the view still writes nothing, still makes no model call to draw a frame, and the version is resolved once at startup so a long watch never claims a release it stopped running.
- The status view acquires a dependency on the `claude` CLI being on the PATH and authenticated — an assumption true of the machine an operator watches from and false of nearly everywhere else, which is why every failure path omits the line rather than reporting it. The consequence worth stating is that its *absence* is silent: a consumer whose CLI is unauthenticated sees no line and no explanation, and `--no-headroom` is the only way to tell the two apart deliberately.
- The default `agent:status` gets ~1.5s slower. That is the price of the line and it is paid on every invocation, not amortised; `--no-headroom` returns the old timing exactly.
- Cost is where the edges are. `blockedBy` rides the issue-list read both consumers already make, so native ordering adds no request per slice. REST is the exception — `sub_issues` and the timeline serve a dependency *count* and no edges — so a migrated spec whose slices declare native blockers falls back to the full-repo scan to learn them, one scan rather than one read per slice, and only when the count says there is something to learn.
